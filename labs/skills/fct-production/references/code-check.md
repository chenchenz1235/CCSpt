# 工装功能实现核对

## 可选项目

仅在用户要求审核软件、核对修改结果时使用。本项不是第三步文件输出的必经门槛；第二步为判断协议能力而读取代码，不等于启动完整审核。第三步的软件修改指导/检查表可以先交付，结果和证据留空。

## 核对基线

软件团队根据已确认的工装方案修改FCT后，以测试点表、目标流程和目标协议逐项验收。先核对本次代码与硬件版本，再为每项给出实现位置及已满足/缺失/错误/待验证结论。缺少实现不能通过删方案项目解决；常量占位、旧结构体或未更新字段均按不符合目标处理。默认只提供核对结果和具体修改建议，用户要求时才改代码。方案阶段发现的同类问题先进入第二步待确认差异，使用者决定处理方式后再列正式修改清单并输出方案。

## 9 代码检测要沿链路核对

不能只看ccspt_fct.c里有没有赋值。读取链为“硬件采样→实时数据→FCT观察结构→组帧→工装解析→判据”；输出链为“工装命令→模式/参数→执行模块→寄存器/引脚→负载→结果检测”。

重点核对：

- 每个回传字段有真实、周期更新的数据生产者；未采样成员或初值不当作测量值。
- FCT输出标志有消费者；仅设置结构体变量不能证明LED、继电器或TX已动作。
- 输入读输入寄存器，输出执行到正确引脚，GPIO/外设复用及极性一致。
- 主/风机各用各自故障来源；采集未完成、停止和故障不被初始零值误判。
- 每轮启动/停止正确处理计时、极值和累计数据；重新测试不能沿用上一轮通过值。
- 命令长度、参数范围、模式限制及响应语义与架构匹配；暂不修改的风险单独记录，不能沉淀成“永远不需要检查”的规则。
- 拖动参数与实际测试电机匹配；测试指令不会与其他速度源竞争；恢复方式和停机条件明确。
- switch分支、发送忙状态、缓冲长度一起看，不能看到缺break就直接断言一定连发两帧。

根据任务范围执行目标构建和必要检查，并分别记录“静态分析”“编译通过”“台架测试”的证据。旧obj文件或代码中存在函数名，不是运行功能已通过的证明。
