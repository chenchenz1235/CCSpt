# 第二步：测试方案确认

前提是第一步项目总览已由用户确认。将项目按状态归组，不重新强制做一轮“检测点确认”。详细针点归属在本步为接线与协议服务。按单面背面针床规划，主要供电可用端子；逐路明确供电和测量相对主供电的隔离/非隔离关系及参考端，具体要求见[测点、表格和协议](points-tables-protocol.md)。流程覆盖所有测项，测试点表仅收录实际扎针点。

## 输出表

固定三列：阶段｜推荐检测方案｜软件对比后的待确认建议。同一状态可一起检测的项目合并写，保持简洁。第三列先写“当前协议架构支持（现状可用／需修改实现）”或“当前协议架构不支持”，再给具体修改建议及确认事项；混合能力分项写明。

|阶段|规划内容|
|---|---|
|1 上电与通信|针板压合、供电，通常等待3～5s。各选择通信收发法的待测外置口依次发送进入FCT并确认（仅做高低状态检测的电流环除外）；固定主测试口，验证相关芯片的软件版本。|
|2 静态检测|工装输出所需电压、电阻、脉冲或开关状态。集中测量电源轨及正常吸合的电源继电器；读取VAC/VDC、VSP、温度、各实采电流零点等已选对象。零点检测时停止/PWM关闭。|
|3 输出组检测|按对象组合组1、组2，确有需要才增加组3。集中检测辅助输出、触点、电流环、FG等；LED通常在其中一组稳定点亮，测一次A-K压降。|
|4 拖动检测|按确认负载、电流与时间执行启动、完成判断、状态/故障读取、停止。多电机在工装允许时同时测试并分别判定。|
|5 可选故障检测|仅安排本项目有硬件基础且用户确认必要的项目。已有故障码可在各阶段读取，不因此增加注入步骤。|
|结束|撤激励、停输出/确认停止、断电放电后松开针板，保存结果。|

这是规划次序，不强迫固件拆成同样阶段。组1联动拖动不与方案冲突，只要静态采样已经结束且不妨碍输出检测，工装按自己的顺序测即可，不默认要求解耦。后续若需新一轮拖动，明确停止、重新启动及数据更新条件。

## 软件支持的边界

- **架构支持**：已有协议和命令框架能承载所需动作；仅改报文传输内容、结构体成员/单位/状态值，补执行/回采逻辑，或将串口输出切为FCT下的GPIO等输出形式。列具体软件修改及兼容影响，不将“架构支持”写成“当前代码已支持”。
- **架构不支持**：所需新命令、转发机制或通信路径在现有框架中无承载能力，需要新增协议功能。列缺口、影响和可选方案，等待用户确认；不先写成最终协议。
- 不因旧FCT字段没更新而取消硬件该测项目。读取正常业务数据生产者及执行路径决定目标，FCT代码用于识别需要补什么。
- 不妨碍产测的产品功能可在FCT改变行为；仍要保留必要保护和电源正常吸合逻辑。

## 多通信口与跨芯片

优先对外口为主口，其他选择通信收发法的待测口只作重复进入FCT收发验证；仅做高低状态检测的电流环安排到输出组，不要求通过电流环发送进入FCT。固定主口后尽量完成所有测试。驱动能否进入、启停、查询，以及主控是否有双向转发分别判断。已有转发要检查请求封装、目标选择、驱动命令解析、回复返回原口、超时及停止后会否被周期命令再次启动。

已有转发框架只需补转发FCT回复分支时，列为架构支持但实现需补。确实不能通过主口完成的功能，才建议保留驱动口等用于部分测试，由用户确认。转发地址、前缀和报文必须根据当前工程核实。

## 确认后衔接第三步

保留确认的测项、分组、主口/例外口、负载与电流、需修改的软件内容、判限及未定参数。第三步据此输出正式文件和独立软件指导；当前软件仍待实现的地方明确标目标要求。用户不同意软件改法时先调整方案，不擅自删测项或新增协议。
